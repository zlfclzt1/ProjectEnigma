# 经典旧世内容版本与来源政策

- 政策状态：生效
- 生效日期：2026-09-08
- 目标版本 ID：`classic-2019-phase-6`
- 关联设计：[游戏设计文档](./game-design-v0.1.md)
- 当前计划：[10–45 级祖尔法拉克阶段实施计划](./zulfarrak-stage-implementation-plan.md)

本文档定义真实内容的统一版本口径、来源优先级和审计要求。它约束职业、专精、种族、副本、Boss、装备、属性、图标、掉落、随机词缀、套装、任务和后续配方等内容事实。

## 1. 唯一目标版本

正式内容统一采用 2019 经典怀旧服最终阶段口径，机器标识固定为：

```text
classic-2019-phase-6
```

当前不接受以下内容混入同一正式注册表：

- 探索赛季规则或重制装备。
- 燃烧的远征前夕及之后的属性改动。
- 后续周年服或其他特殊服务器专属规则。
- 零售版本同名物品、Boss 或任务数据。

未来若支持其他版本，必须增加新的明确版本 ID、隔离内容包和兼容设计，不能改变 `classic-2019-phase-6` 的含义。

## 2. 外部事实与设计决定

内容元数据必须区分两类来源。

### 2.1 外部事实 `source-fact`

用于记录可以从经典资料核对的事实，例如：

- 物品名称、品质、栏位、需求等级、图标和原始属性。
- Boss 与装备的真实掉落关系。
- 原始掉率或用于计算相对权重的数据。
- 副本路线、Boss 身份、任务目标和任务奖励。
- 随机词缀名称、档位、属性和权重。

每条外部事实必须包含：

```text
kind = source-fact
provider
gameVersion = classic-2019-phase-6
url
verifiedAt
```

有稳定外部 ID 的内容还应填写 `externalId`。来源 URL 应尽量指向可复查的具体条目或固定仓库文件，而不是网站首页。

### 2.2 设计决定 `design-decision`

用于记录为了放置玩法主动设计的数据，例如：

- 压缩后的副本时长。
- Boss 坦克、治疗和输出需求。
- 成功率上下限。
- 经验、资金和首杀奖励。
- 公会升级条件与费用。
- 稀有 Boss 在本游戏中的出现概率。

设计决定必须使用 `provider = manual`，不要求填写经典内容版本。说明中应明确这是游戏规则，不得写成对原版事实的引用。

## 3. 来源职责

当前允许的提供方及主要职责如下：

| Provider | 主要用途 |
|---|---|
| `wowhead-classic` | 物品 ID、名称、图标、品质、需求等级和原始属性；任务与 NPC 条目交叉核对 |
| `atlasloot-classic` | 副本 Boss 与装备关系、掉落池和相对掉率交叉核对 |
| `warcraft-wiki` | 副本、Boss、路线、任务和机制背景交叉核对 |
| `manual` | 放置玩法时长、概率、经验、资金、解锁和其他明确设计决定 |

单一资料无法稳定证明某项事实时，应保留多个 `source-fact`。来源之间发生冲突时，不得静默选择：需要在 `notes` 中记录差异、选择依据和待复查项。

## 4. 掉落来源边界

- Boss 专属装备只进入对应 Boss 掉落池。
- 原版没有专属装备池的 Boss 可以没有装备掉落。
- 任务奖励只能通过成员副本任务发放。
- 世界掉落当前不进入正式副本池。
- 材料、配方、垃圾物品和任务物品在相应系统开放前不进入装备池。
- Boss 保证掉落数量属于游戏规则，需要使用 `balanceOverride` 记录；池内物品关系与相对权重仍属于外部事实。

不得为了保证每个路线节点都有装备反馈，把任务奖励或世界掉落伪装成 Boss 专属装备。

## 5. 数值覆盖

真实内容与游戏平衡值必须分开保存：

- 原始事实保存在内容字段及 `source-fact` 中。
- 游戏主动修改的字段通过 `balanceOverride.fields` 列出。
- `balanceOverride.reason` 解释玩法原因。
- `balanceOverride.decidedAt` 使用实际决定日期。

一次覆盖不能抹去原始事实来源。若界面只展示原始值、领域公式使用平衡值，两者都必须能从数据和代码中追踪。

## 6. 调查和录入流程

每项真实内容按以下顺序处理：

1. 确认目标属于 `classic-2019-phase-6`。
2. 记录稳定名称、外部 ID 和具体来源 URL。
3. 使用第二来源交叉核对掉落关系、随机词缀或任务奖励。
4. 将无法确认的字段标记为待调查，不使用猜测值补齐。
5. 单独记录游戏平衡覆盖。
6. 运行 Schema、内容引用和专项审计。
7. 在内容研究提交和正式数据提交之间保留可追踪关系。

## 7. 日期规则

- `verifiedAt` 表示最近一次实际核对外部资料的日期。
- `decidedAt` 表示团队作出游戏设计决定的日期。
- 更新说明文字但没有重新核对资料时，不得顺手刷新 `verifiedAt`。
- 修改真实数据时必须重新核对来源，并按实际日期更新 `verifiedAt`。

## 8. 自动校验要求

内容 Schema 必须保证：

- `source-fact` 不能使用 `manual`。
- `source-fact` 必须提供 URL。
- `source-fact` 必须声明 `classic-2019-phase-6`。
- 未知或排除的版本 ID 无法通过解析。
- `design-decision` 必须使用 `manual`。
- 覆盖字段不能重复，且必须提供原因和日期。

后续内容审计还应检查：

- 真实装备属性的外部 ID 与物品 ID 一致。
- Boss 池没有任务奖励或世界掉落。
- 同一物品没有被无依据地关联到多个 Boss。
- 随机词缀档位覆盖物品等级。
- 内容文件中的外部事实没有缺失版本标记。

## 9. 提交验收清单

任何新增或修改真实内容的提交都必须回答：

- 使用的是不是 `classic-2019-phase-6`？
- 外部事实是否有具体 URL 和核对日期？
- 掉落关系是否经过第二来源交叉核对？
- 设计数值是否被错误写成外部事实？
- 是否混入任务奖励、世界掉落或其他版本内容？
- 是否运行了内容校验和相关专项审计？

无法肯定回答时，不应合入正式内容。
